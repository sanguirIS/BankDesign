# Releases

This document describes how **BankDesign** is versioned and released. The actual
release notes for every version live in [CHANGELOG.md](CHANGELOG.md), which is
also consumed by the [release workflow](.github/workflows/release.yml) to
generate the notes for each GitHub Release.

## Versioning

BankDesign follows [Semantic Versioning](https://semver.org/):

- **MAJOR** (`x.0.0`) — breaking changes (removed APIs, restructuring, breaking config changes).
- **MINOR** (`0.x.0`) — new features added in a backwards-compatible way.
- **PATCH** (`0.0.x`) — backwards-compatible bug fixes and small improvements.

Release tags follow the format `v<version>` (e.g. `v1.0.0`).

## Changelog Format

[CHANGELOG.md](CHANGELOG.md) is owned and generated by
[release-please](https://github.com/googleapis/release-please) from
Conventional Commit history (release-please v4+ format):

```markdown
## [1.1.0](https://github.com/owner/repo/compare/v1.0.0...v1.1.0) (2026-08-09)

### Features

* feat: …

### Bug Fixes

* fix: …
```

- Section headings are derived from the `changelog-sections` mapping in
  [`.release-please-config.json`](.release-please-config.json).
- Versions are written **without** the `v` prefix so the release workflow can
  match them to the pushed tag (`v1.0.0` → `## [1.0.0]`).

## How a Release Is Made

Releases are fully automated with [release-please](https://github.com/googleapis/release-please):

1. Merge changes to `main` using [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `perf:`, `docs:`, …).
2. The [release-please workflow](.github/workflows/release-please.yml) opens a **release PR** that bumps `package.json`, moves the commits into a new `CHANGELOG.md` entry, and updates `.release-please-manifest.json`.
3. **Merge the release PR** — that's the whole process. release-please then tags the merge commit (`vX.Y.Z`).
4. Pushing the `v*` tag automatically triggers the
   [Release workflow](.github/workflows/release.yml), which:
   - **fails if `CHANGELOG.md` has no `## [<version>]` entry for the tag** (the release process is enforced),
   - builds the static export (`bun run build`),
   - packages the site into `dist/bankdesign-<tag>.tar.gz`,
   - extracts the matching `CHANGELOG.md` entry as the release notes,
   - publishes a GitHub Release with the archive attached,
   - deploys the export to **Netlify** (production) when the `NETLIFY_AUTH_TOKEN` and `NETLIFY_SITE_ID` secrets are configured, and
   - deploys the export to **GitHub Pages**.

> **Note:** because release-please regenerates `CHANGELOG.md` from commit history, the hand-written Keep-a-Changelog formatting (and the `[Unreleased]` section) is replaced by release-please's format on the first release PR.

> **Note:** for the tag created by release-please to trigger the Release workflow, add a `RELEASE_PLEASE_TOKEN` (classic PAT with `repo` scope) to repository secrets. Without it the workflow falls back to `GITHUB_TOKEN`, which GitHub deliberately does not use to trigger downstream tag-push workflow runs.

### Deployment targets

- **Netlify** — deploys the root-path export (`build/`). Add `NETLIFY_AUTH_TOKEN` and `NETLIFY_SITE_ID` to the repository secrets (Settings → Secrets and variables → Actions) to enable it; without them the step is skipped.
- **GitHub Pages** — deploys a subpath build (`NEXT_PUBLIC_BASE_PATH=/<repo-name>`). Enable **Settings → Pages → Source: GitHub Actions** once; no secrets required. The site lives at `https://<owner>.github.io/<repo-name>/`. If you later point Pages at a custom domain or user/org site (root path), remove the `NEXT_PUBLIC_BASE_PATH` override in the workflow.
